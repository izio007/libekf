# Проверяем требования к поведению

Для каждой проверки должны быть понятны **требование, условия, ожидаемый результат и допустимая ошибка**. Ожидание задаётся до запуска и имеет независимое основание: геометрию, физический закон, аналитическое решение или проверяемое свойство задачи.

Проверка обращается к входам и выходам функции. Изменение внутренней организации кода при сохранении результата не должно требовать переписывать проверку. Проверки формул допустимы как дополнительные математические проверки; они не заменяют проверку поведения всей функции.

## Примеры для libekf

| Требование к поведению | Проверочный случай | Что должно получиться |
|---|---|---|
| Каждый источник соответствует своему физическому смыслу | Станция смещена от самолёта на 3 и 4 м по двум осям | Дальномер показывает 5 м |
| Радиовысотомер рассматривает всю диаграмму | Наклонная поверхность, перепад 10 м, наклон 45°, диаграмма 120° | Ближайшая дальность — $10/\sqrt2$ м; измерение не подменяется вертикальными 10 м |
| Неоднозначность не скрывается | Две поверхности дают одинаковый ближайший возврат | Единственная гладкая поправка не объявляется пригодной |
| Смена координат сохраняет физический результат | Один случай выражен в двух местных системах | Положение, измерение и преобразованная погрешность согласуются |
| Изменение единиц не меняет решения о согласованности | Одно расхождение и его погрешность записаны в разных единицах | Безразмерная мера расхождения одинакова |
| Недопустимые данные не применяются | Неверные единицы, устаревший отсчёт, недостоверная карта или выход за допустимый диапазон | Получаем явный отказ; данные не переименовываются и не исправляются молча |

Для приведённых геометрических случаев допуски характеризуют вычисление на заданных числах. Они не являются требованиями к точности реальных приборов. Границы реального применения задаются отдельно по исходным требованиям.

## Как хранить и запускать

Одна группа связанных функций — один файл испытаний с именованными проверками требований. Разные входные случаи записываются прямо в нём. Новый файл данных или настроек нужен только для самостоятельных существенных исходных данных.

Не нужны отдельные JSON-файлы на каждый опыт, копии одного сценария, проверки текста исходника, порядка внутренних вызовов или существования служебного отчёта. Общие вспомогательные вычисления остаются рядом с проверками.

Вызов возвращает результат по каждой проверке. Сбой одной проверки не должен скрывать результаты остальных. История запусков и служебные файлы находятся в runtime/. Проверки поведения сохраняются после исправлений.

Рисунок поясняет, что именно сравнивается: оси, единицы, входные условия, ожидаемая и вычисленная величины. Сохранённый рисунок включается в теорию обычной ссылкой. Рисунок не заменяет численного критерия. Для его экспорта не создаются отдельные испытания или процедуры приёмки.

В теории сначала объясняется задача понятными русскими терминами, затем приводятся рисунок, последовательность работы и ограничения. Формулы сопровождаются объяснениями величин. Обозначения из кода не заменяют предметного описания.

## Основания и открытые примеры

- [NASA, SWE-066: выполнение испытаний](https://swehb.nasa.gov/pages/viewpage.action?pageId=16458494) — связь проверок с требованиями и анализ результатов.
- [NASA, SWE-068: оценка результатов](https://swehb.nasa.gov/spaces/SWEHBVB/pages/32604541/SWE-068%2B-%2BEvaluate%2BTest%2BResults) — сравнение факта с заранее установленным ожиданием и критерием.
- [MathWorks: проверки локальными функциями одного файла](https://www.mathworks.com/help/matlab/matlab_prog/function-based-unit-tests.html) — компактная организация независимых проверок.

В проекте применяются эти принципы; обязательные организационные процедуры NASA для libekf не назначаются. Отдельный реестр проверок и новая система управления испытаниями не создаются.
